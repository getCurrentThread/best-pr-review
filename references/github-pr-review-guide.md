## 1. 한눈에 보기 (TL;DR)

- 코멘트 앞에 **라벨**을 붙여 의도와 강도를 밝힌다 → `issue (blocking):`, `suggestion:`, `nitpick:`, `question:`, `praise:`
- **사람이 아니라 코드**를 주어로 쓴다.
- **왜**를 설명한다 — 재현 조건, 영향, 근거(문서·데이터·컨벤션 링크).
- 문제만 짚을지, 해결책까지 줄지 균형을 잡는다. 한두 줄 수정은 GitHub **`suggestion` 블록**으로.
- 잘한 점은 **구체적으로** 칭찬한다. (거짓 칭찬은 금물)
- 승인 기준은 "완벽한가"가 아니라 **"코드베이스가 확실히 나아지는가"**.
- **빠르게** 응답한다 — 첫 응답은 최대 1영업일 이내.
- 리뷰를 제출할 때는 **요약 코멘트**로 결론과 다음 행동을 정리하고, 제출 상태(Approve / Comment / Request changes)를 코멘트 강도와 맞춘다.

## 2. 좋은 리뷰의 원칙

### 2.1 승인 기준: 완벽보다 "개선"

Google 가이드의 최상위 원칙은, 변경이 완벽하지 않더라도 **시스템 전체의 코드 건강도를 확실히 개선하는 상태라면 승인 쪽으로 기울라**는 것입니다. 완벽한 코드는 없고 더 나은 코드만 있으므로, 사소한 다듬기까지 모두 요구하며 PR을 며칠씩 묶어두지 않습니다. 반대로 코드 건강도를 확실히 **악화**시키는 변경은 (긴급 상황이 아닌 한) 승인하지 않습니다.

### 2.2 코드에 대해 말하고, 사람에 대해 말하지 않는다

| ❌ 사람이 주어 | ✅ 코드가 주어 |
|---|---|
| "왜 **이렇게** 짜셨어요? 스레드 쓸 이유가 없잖아요." | "이 구간은 I/O 대기가 없어 병렬화 이득이 없는데, 스레드 풀이 들어가면서 종료 처리와 예외 전파가 복잡해졌어요. 단일 스레드로 두는 편이 읽기·테스트 모두 쉬울 것 같습니다." |

### 2.3 "왜"를 설명한다

코멘트에 이유가 붙으면 작성자는 **같은 실수를 다른 곳에서도 스스로 피할 수 있습니다.** 근거는 다음 중 하나 이상이면 좋습니다.
- 구체적인 실패 시나리오 (어떤 입력 → 어떤 결과)
- 측정값·데이터 (쿼리 수, 응답 시간, 메모리)
- 팀 컨벤션·스타일 가이드·공식 문서 링크

### 2.4 해결은 작성자 몫, 하지만 필요하면 직접 안내

수정 책임은 기본적으로 작성자에게 있습니다. 문제만 짚고 작성자가 판단하게 하면 학습 효과가 크고, 코드에 더 가까운 작성자가 더 나은 해법을 찾기도 합니다. 다만 상황에 따라 구체적 지시나 코드 제안이 더 도움이 될 때도 있으니 **균형**을 잡습니다.

### 2.5 칭찬도 리뷰다

사람은 잘한 것을 강화받으며 배웁니다. 지저분한 알고리즘을 정리했거나, 테스트가 훌륭하거나, 리뷰어가 새로 배운 게 있다면 **무엇이 왜 좋았는지** 말해 줍니다. Conventional Comments는 리뷰마다 진심 어린 칭찬을 최소 하나 남기길 권하되, 형식적인 거짓 칭찬은 오히려 해롭다고 경고합니다.

### 2.6 의견보다 사실, 스타일은 가이드가 결정

- 기술적 사실과 데이터가 개인 취향보다 우선합니다.
- 스타일 문제는 **스타일 가이드가 절대 기준**입니다. 가이드에 없는 순수 스타일은 개인 취향이므로 강요하지 않습니다(기존 코드와 일관성 정도만 요청).
- 설계는 "취향"이 아니라 원칙의 문제입니다. 여러 방식이 동등하게 타당하다는 근거가 있으면 **작성자의 선택을 존중**합니다.

### 2.7 응답 속도

- 집중 작업 중이 아니라면 요청이 오면 곧 리뷰합니다. **첫 응답은 최대 1영업일.**
- 코딩에 몰입 중이라면 끊지 말고 다음 쉬는 지점에서 봅니다.
- 전체 리뷰가 당장 어려우면 ① 언제 볼 수 있는지 알리거나 ② 다른 리뷰어를 추천하거나 ③ 큰 그림 코멘트부터 먼저 보냅니다.
- 리뷰 과정에 대한 불만 상당수는 **응답을 빠르게** 하는 것만으로 해소됩니다.

### 2.8 "설명"은 리뷰 창이 아니라 코드에 남기게 한다

이해가 안 돼서 질문했다면, 이상적인 결과는 작성자가 **코드를 더 명확하게 고치는 것**(또는 필요한 주석 추가)입니다. 리뷰 툴에만 남은 설명은 미래의 코드 독자에게 전달되지 않습니다.

## 3. 무엇을, 어떤 순서로 볼까

### 3.1 리뷰 순서

1. **PR 설명부터 — 이 변경이 애초에 타당한가?**
   타당하지 않다면 나머지를 보기 전에 **즉시, 정중하게, 대안과 함께** 알립니다. (예시: [7.11](#711-방향-자체를-반려할-때-pr-수준))
2. **핵심 파일의 설계를 먼저 확인**
   큰 설계 문제가 보이면 나머지 리뷰를 마치기 전이라도 **바로 전달**합니다. 작성자는 이미 이 PR 위에 후속 작업을 쌓고 있을 수 있고, 큰 재작업일수록 일찍 시작해야 하기 때문입니다.
   PR이 너무 커서 핵심을 모르겠다면 어디부터 볼지 묻거나 분할을 요청합니다.
3. **나머지 파일을 빠짐없이 순서대로**
   테스트를 먼저 읽으면 변경의 의도를 파악하기 쉬울 때가 많습니다.

### 3.2 볼 것 (중요도 순)

| 관점 | 확인 질문 |
|---|---|
| 설계 | 이 위치·이 구조가 맞는가? 시스템과 잘 맞물리는가? |
| 기능 | 의도대로 동작하는가? 엣지 케이스, 동시성, 사용자 영향은? |
| 복잡도 | 더 단순할 수 있는가? **지금 필요 없는 일반화(과설계)** 는 없는가? |
| 테스트 | 적절한 테스트가 있는가? 코드가 깨지면 테스트가 실패하는가? |
| 네이밍 | 이름이 역할을 충분히, 과하지 않게 설명하는가? |
| 주석 | "무엇"이 아니라 **"왜"** 를 설명하는가? |
| 스타일·일관성 | 스타일 가이드를 따르는가? (가능하면 린터/포매터로 자동화) |
| 문서 | README, 설정 예시, 마이그레이션 가이드 갱신이 필요한가? |

## 4. GitHub 리뷰 제출 유형 고르기

| 유형 | 의미 | 이럴 때 |
|---|---|---|
| **Comment** | 승인도 차단도 아닌 일반 피드백 | 질문이 풀려야 판단 가능할 때, 부분 리뷰만 했을 때, 의견만 남길 때 |
| **Approve** | 머지해도 좋다 | blocking 이슈가 없을 때 (non-blocking 코멘트는 남겨도 됨) |
| **Request changes** | 머지 전 반드시 해결 필요 | 버그·보안·데이터 손실·컨벤션 위반 등 blocking 이슈가 있을 때 |

**팁**

- **Start a review로 코멘트를 모아서 한 번에 제출**하세요. 코멘트를 하나씩 달면 알림이 여러 번 갑니다.
- 저장소의 브랜치 보호 규칙/룰셋 설정에 따라 *Request changes* 는 머지를 막을 수 있으니, 정말 blocking일 때만 씁니다.
- **"코멘트 남기고 승인 (LGTM with comments)"** 이 효율적인 경우가 많습니다. 아래 중 하나라도 해당하면 남은 코멘트가 있어도 승인할 수 있습니다.
  - 작성자가 남은 코멘트를 알아서 잘 처리할 것이라 확신할 때
  - 남은 코멘트가 반드시 반영할 필요는 없을 때
  - import 정렬, 오타, 미사용 의존성 제거처럼 사소할 때
  → 어떤 경우인지 **요약 코멘트에 명시**합니다. 시차가 큰 협업에서 특히 유용합니다.
- 리뷰 범위 밖 제안은 GitHub에서 코멘트를 기반으로 **새 이슈를 만들어** 추적할 수 있습니다.

## 5. 코멘트 형식 체계 (라벨링)

리뷰 코멘트가 글로만 전달되면 표정·말투가 빠져 **가벼운 의견이 무거운 지적으로 읽히기 쉽습니다.** 라벨은 의도와 강도를 명시해 이런 오해를 줄입니다. 대표적인 체계 네 가지를 소개합니다. 팀에서는 **하나만 골라** 일관되게 쓰는 걸 권합니다.

### 5.1 Conventional Comments (가장 널리 쓰이는 범용 포맷)

**형식**

```
<label> [decorations]: <subject>

[discussion]
```

- `label`: 코멘트 종류 (하나)
- `decorations` (선택): 괄호 안 쉼표 구분 부가 정보 — `(blocking)`, `(non-blocking)`, `(if-minor)`, `(security)`, `(performance)`, `(test)` 등
- `subject`: 핵심 메시지 한 줄
- `discussion` (선택): 근거, 맥락, 다음 단계

**주요 라벨**

| 라벨 | 의미 | 기본 강도 |
|---|---|---|
| `praise:` | 진심으로 좋은 점. 리뷰마다 하나 이상 권장 | — |
| `nitpick:` | 사소한 취향 수준의 요청 | non-blocking |
| `suggestion:` | 개선 제안. **무엇을**, **왜** 바꾸는지 명확히 | decoration으로 명시 |
| `issue:` | 구체적 문제 지적. `suggestion`과 짝지어 쓰길 권장. 확신이 없으면 `question` | 보통 blocking |
| `todo:` | 작지만 꼭 필요한 변경 | blocking |
| `question:` | 우려는 있으나 확실치 않을 때 확인 요청 | 상황별 |
| `thought:` | 리뷰 중 떠오른 아이디어. 후속 작업·멘토링의 씨앗 | non-blocking |
| `chore:` | 머지 전 필요한 절차성 작업. 절차 문서 링크 첨부 권장 | blocking |
| `note:` | 알아두면 좋은 정보 | non-blocking |

확장 라벨로 `typo:`(오타), `polish:`(문제는 없지만 품질 향상), `quibble:`(nitpick의 순화 표현)도 씁니다.

**Decoration 의미**

| decoration | 의미 |
|---|---|
| `(blocking)` | 해결될 때까지 머지 불가 |
| `(non-blocking)` | 머지를 막지 않음 |
| `(if-minor)` | 변경이 사소한 범위라면 반영해 달라는 뜻 (작성자 재량) |

### 5.2 Google 심각도 접두사 (가장 간단)

| 접두사 | 의미 |
|---|---|
| (접두사 없음) | 반영 필요 |
| `Nit:` | 사소함. 하는 게 맞지만 큰 영향 없음 |
| `Optional:` / `Consider:` | 좋은 아이디어 같지만 필수 아님 |
| `FYI:` | 이번 PR에서 할 일은 아님. 향후 참고 |

라벨이 없으면 작성자는 **모든 코멘트를 필수로 받아들이기 쉽다**는 것이 이 접두사를 쓰는 이유입니다.

### 5.3 국내 사례 ① 뱅크샐러드 Pn 룰

강조 정도를 P1~P5로 표기하고, **GitHub 리뷰 상태와 매핑**한 것이 특징입니다.

| 태그 | 의미 (요약) | 작성자 대응 | 리뷰 상태 |
|---|---|---|---|
| **P1** | 반드시 반영 (중대한 오류 가능성 등) | 반영하거나, 반영할 수 없는 합리적 근거로 설득 | Request changes |
| **P2** | 적극적으로 고려 | 수용, 어렵다면 의견을 들어 토론 | Request changes |
| **P3** | 웬만하면 반영 | 수용, 어렵다면 이유 설명 또는 후속 계획(티켓) 명시 | Comment |
| **P4** | 반영 여부 자유 | 무시해도 됨 | Approve |
| **P5** | 사소한 의견 | 무시해도 됨 | Approve |

함께 쓰는 **D-n 룰**: 리뷰 요청 시 머지 희망 일정을 표기 — `D-0`(긴급, 즉시 리뷰), `D-2`(영업일 2일 이내, 기본값), 여유 있으면 `D-3`~`D-5`.

### 5.4 국내 사례 ② 화해 L0~L5 (Netlify Feedback Ladder 응용)

Netlify의 Feedback Ladder(Mountain → Boulder → Pebble → Sand → Dust, 무거운 순)를 조직에 맞게 바꾼 템플릿입니다.

| 태그 | 언제 쓰나 (요약) |
|---|---|
| `[L0-리뷰불가]` | PR 설명이 부족하거나, 변경이 너무 크거나, 설계가 잘못돼 전면 재작업이 필요해 리뷰 자체가 어려울 때 |
| `[L1-변경요청]` | 기능 결함·심각한 품질 저하·팀 컨벤션 위반 → 머지 전 필수 수정 |
| `[L2-변경협의]` | 가급적 머지 전 반영, 바로 후속 작업으로 처리해도 됨. 이견 시 토론 |
| `[L3-중요질문]` | 답을 들어야 정확한 리뷰가 가능할 때 |
| `[L4-변경제안]` | 더 나은 방안 같지만 작성자 판단에 맡길 때 |
| `[L5-참고의견]` | 우열은 모르겠으나 다른 방법·참고 정보 공유 |

### 5.5 체계 간 대략적 대응표

> 체계마다 경계가 조금씩 다르므로 "대략" 이렇게 대응된다고 보면 됩니다.

| 강도 | Conventional Comments | Google | 뱅크샐러드 | 화해 | 리뷰 상태 |
|---|---|---|---|---|---|
| 리뷰 진행 불가 | `issue (blocking)` + PR 수준 코멘트 | — | P1 | L0 | Request changes / Comment |
| 머지 전 필수 | `issue (blocking)`, `todo:`, `chore:` | (접두사 없음) | P1 | L1 | Request changes |
| 강하게 권장, 협의 가능 | `suggestion (blocking)` | (접두사 없음) | P2 | L2 | Request changes |
| 판단 위해 답 필요 | `question (blocking)` | — | — | L3 | Comment |
| 웬만하면 반영 | `suggestion (non-blocking)` | `Consider:` | P3 | L4 | Comment / Approve |
| 선택 | `suggestion (if-minor)`, `polish:` | `Optional:` | P4 | L4 | Approve |
| 사소함 | `nitpick:` | `Nit:` | P5 | L5 | Approve |
| 참고 정보 | `note:`, `thought:` | `FYI:` | P5 | L5 | Approve |
| 칭찬 | `praise:` | — | — | — | (모든 상태) |

## 6. 좋은 코멘트의 5요소와 기본 템플릿

| 요소 | 내용 | 예 |
|---|---|---|
| ① 라벨 | 의도·강도 | `issue (blocking):` |
| ② 관찰 | 무엇을, 어디서 봤는지 | "`items`가 빈 배열이면 L42에서…" |
| ③ 이유 | 왜 문제/개선인지 (영향·근거) | "결제 페이지가 흰 화면이 됩니다" |
| ④ 제안 | 대안, 코드, 또는 질문 | "빈 배열이면 0 반환 / suggestion 블록" |
| ⑤ 처리 기대 | 이 PR에서? 후속 이슈? 선택? | "이번 PR에서 부탁드려요" |

**기본 템플릿**

```markdown
**<label> (<decorations>):** <한 줄 요약>

<관찰: 어떤 조건에서 무슨 일이 일어나는지>
<이유: 왜 문제인지 / 근거 링크>

<제안: 대안 설명 또는 suggestion 블록>
<처리 기대: 이 PR에서 / 후속 이슈로 / 선택>
```

> **정중함 ≠ 모호함.** blocking 이슈를 "혹시… 괜찮으시면…"처럼 쿠션어로 감싸면 강도가 흐려집니다. 말투는 정중하게, 강도는 **라벨로 분명하게** 표시하세요.

## 7. 상황별 Bad → Good 예시

### 7.1 버그 지적 (blocking)

```ts
// CartSummary.tsx
const firstPrice = cart.items[0].price;
```

❌ **Bad**
> 이거 터져요.

✅ **Good**
> **issue (blocking):** `cart.items`가 빈 배열이면 `cart.items[0].price`에서 TypeError가 발생합니다.
>
> 장바구니를 모두 비운 뒤 결제 페이지로 진입하면 재현돼요(스테이징에서 확인). 이 경우 결제 화면 전체가 렌더링되지 않습니다.
>
> 빈 배열이면 0을 반환하거나, 상위에서 결제 버튼을 비활성화하는 방법 중 하나가 필요해 보여요. 빈 장바구니 케이스 테스트도 함께 추가 부탁드립니다.

**포인트**: 재현 방법 + 사용자 영향 + 해결 방향 + 테스트 요청.

---

### 7.2 불필요한 복잡도 (사람 대신 코드를 주어로)

❌ **Bad**
> 왜 굳이 캐시를 직접 구현하셨어요?

✅ **Good**
> **suggestion:** 여기서 LRU 캐시를 직접 구현했는데, 이미 의존성에 있는 `lru-cache`로 대체하면 만료·용량 관리 코드 80줄 정도가 줄고 테스트 부담도 덜 것 같아요.
>
> 혹시 직접 구현해야 하는 이유(특정 eviction 정책 등)가 있었다면 알려주세요. 그렇다면 그 이유를 클래스 상단 주석으로 남겨두면 좋겠습니다.

**포인트**: 의도를 추궁하지 않고, 대안의 이득을 수치로 제시하고, 작성자가 맞을 가능성을 열어 둠.

---

### 7.3 의도 확인 질문

```py
MAX_RETRY = 5
```

❌ **Bad**
> 5는 왜요?

✅ **Good**
> **question:** 재시도 횟수를 5로 잡은 근거가 있을까요? 외부 API rate limit이 분당 10회라, 동시 요청이 몰리면 재시도만으로 한도를 금방 소진할 것 같아 여쭤봐요.
>
> 근거가 있다면 상수 옆 주석으로 남겨주시면 다음 사람에게도 도움이 될 것 같습니다.

**포인트**: 왜 묻는지(우려)를 함께 밝히면 질문이 공격처럼 읽히지 않음. 답을 코드에 남기도록 유도.

### 7.4 네이밍 nit

```ts
const data2 = orders.filter((o) => o.status === "PENDING");
```

❌ **Bad**
> 변수명 이상함

✅ **Good**
> **nitpick (non-blocking):** `data2`보다 내용이 드러나는 이름이면 아래 루프가 읽기 쉬울 것 같아요.
>
> ```suggestion
> const pendingOrders = orders.filter((o) => o.status === "PENDING");
> ```

**포인트**: 사소한 건 라벨로 강도를 낮추고, 클릭 한 번으로 반영되도록 suggestion 블록 제공.

---

### 7.5 보안 이슈

```py
query = f"SELECT * FROM users WHERE name LIKE '%{keyword}%'"
cursor.execute(query)
```

❌ **Bad**
> 이건 좀 위험한데요…

✅ **Good**
> **issue (blocking, security):** 사용자 입력 `keyword`가 쿼리 문자열에 그대로 들어가 SQL 인젝션이 가능합니다.
>
> 예를 들어 `keyword`에 `' OR '1'='1`이 들어오면 전체 사용자 목록이 반환됩니다. 파라미터 바인딩으로 바꿔주세요.
>
> ```suggestion
> query = "SELECT * FROM users WHERE name LIKE %s"
> cursor.execute(query, (f"%{keyword}%",))
> ```
>
> 같은 패턴이 `search_products()`(L120)에도 있어서 함께 확인 부탁드립니다.

**포인트**: 공격 입력 예시로 위험을 구체화, 수정안 제공, 같은 패턴의 다른 위치까지 짚음.

---

### 7.6 테스트 누락

❌ **Bad**
> 테스트 없네요.

✅ **Good**
> **suggestion (test):** 할인 계산에 경계값 테스트가 없어요. 할인율 0%·100%, 쿠폰 중복 적용 케이스를 추가하면 다음 정책 변경 때 회귀를 잡기 좋을 것 같습니다.
>
> `discount.spec.ts`의 기존 테이블 테스트에 행만 몇 개 추가하면 될 것 같아요.

### 7.7 성능 이슈 (데이터로 말하기)

```py
for order in Order.objects.filter(user=user):
    print(order.product.name)
```

❌ **Bad**
> 이거 느릴 것 같은데요.

✅ **Good**
> **issue (performance):** 루프 안에서 `order.product`에 접근할 때마다 쿼리가 하나씩 나가는 N+1 패턴이에요. 주문 100건이면 쿼리가 101번 실행됩니다(로컬 debug toolbar로 확인).
>
> ```suggestion
> for order in Order.objects.filter(user=user).select_related("product"):
>     print(order.product.name)
> ```
>
> 주문 내역 페이지는 트래픽이 많은 화면이라 이번 PR에서 반영해 주시면 좋겠어요.

## 8. GitHub suggestion 블록 활용

리뷰어가 제안한 코드를 작성자가 **버튼 한 번으로 커밋**할 수 있는 기능입니다. 오타·네이밍·한두 줄 수정에 특히 좋습니다.

**사용법**

1. PR의 **Files changed** 탭에서 줄 번호 옆 `+` 아이콘 클릭
   - 여러 줄: 첫 줄 번호 클릭 후 드래그, 또는 `Shift`+마지막 줄 번호 클릭
2. 코멘트 박스의 suggestion 아이콘을 누르거나 직접 블록 작성
3. 블록 **위에** 왜 바꾸는지 설명을 적고 **Start a review**로 모아 제출

**문법**

````markdown
**suggestion:** 합계 계산은 reduce로 한 줄에 표현하면 의도가 더 잘 보여요.

```suggestion
const total = items.reduce((sum, item) => sum + item.price, 0);
```
````

**주의**

- suggestion 블록 내용은 **선택한 줄 전체를 대체**합니다. 여러 줄을 선택했다면 바뀌지 않는 줄도 블록에 포함해야 합니다.
- 들여쓰기까지 그대로 반영되니 원본 들여쓰기를 맞춥니다.
- 큰 리팩터링은 suggestion보다 설명 + 방향 제시가 낫습니다.

## 10. 반론(pushback)에 응답하기

### 10.1 원칙

1. **먼저 작성자가 맞는지 진지하게 검토한다.** 작성자는 코드에 더 가까이 있어 리뷰어가 못 본 것을 알 때가 많습니다. 맞다면 깔끔하게 인정하고 코멘트를 철회합니다.
2. **동의하지 않는다면**, 상대의 논지를 이해했음을 보여주면서 **추가 근거**를 제시합니다. "들었지만 동의하지는 않는다"를 정중하게 전달합니다.
3. **"나중에 정리할게요"** 는 조심합니다. 경험적으로 바로 하지 않으면 대부분 잊힙니다. 이 PR이 **새로 만든 복잡도**는 지금 정리하는 게 원칙이고, 정말 미뤄야 한다면 **이슈를 지금 만들고** 코드에 이슈 번호가 달린 TODO를 남깁니다.
4. 코멘트로 합의가 어렵다면 **짧은 통화/대면**으로 이야기하고, **결론을 PR에 기록**합니다. 그래도 안 되면 테크 리드·메인테이너 등에게 에스컬레이션합니다. 합의가 안 된다는 이유로 PR을 방치하지 않습니다.

### 10.2 예시 ① 작성자가 맞을 때 — 깔끔하게 철회

> **작성자:** 결제 SDK가 동기 콜백만 지원해서 async로 바꾸기 어렵습니다.
>
> **리뷰어:** 아, SDK 제약이 있었군요. 제가 놓쳤네요. 이 코멘트는 철회할게요!
> **nitpick:** 그 제약을 함수 위 주석으로 한 줄 남겨두면 다음에 같은 질문이 안 나올 것 같아요.

### 10.3 예시 ② 리뷰어 의견을 유지할 때 — 근거와 타협안

> **작성자:** 일정이 빠듯해서 일단 머지하고 다음 PR에서 리팩터링할게요.
>
> **리뷰어:** 일정 압박 이해합니다. 다만 이 중복은 이번 PR에서 새로 생긴 거라, 지금 정리하는 게 비용이 가장 적을 것 같아요. 두 핸들러의 공통 검증만 `validateOrder()`로 빼면 20줄 내외일 것 같은데 이번에 가능할까요?
> 정말 어렵다면 후속 이슈를 지금 만들고 이슈 번호를 TODO에 남겨주세요. 그 조건이면 승인하겠습니다.

## 11. 표현 바꾸기 & 안티패턴

### 11.1 표현 바꾸기

| 피할 표현 | 바꾼 표현 |
|---|---|
| "왜 이렇게 했어요?" | "이 방식을 고른 이유가 궁금해요. X 상황에서 Y가 걱정돼서요." |
| "틀렸어요." | "입력이 Z일 때 결과가 달라질 것 같아요. (재현: …)" |
| "그냥 ~하면 되잖아요." / "당연히 ~죠." | "~하면 A 측면에서 이득이 있을 것 같아요. (근거 링크)" |
| "(당신이) 놓쳤네요." | "이 분기에서 null 처리가 빠져 있어요." |
| "별로네요." | 무엇이 왜 문제인지 구체적으로 |
| "?" 혹은 "🤔" 만 달기 | 무엇이 궁금한지 문장으로 |
| 라벨 없이 "~해주세요" 나열 | 각 코멘트에 강도 라벨 |

### 11.2 영어 오픈소스 PR용 표현

| 의도 | 표현 |
|---|---|
| 제안 | "What do you think about …?" / "Consider …" / "Could we …?" |
| 질문 | "I'm curious why … — is it because …?" |
| 이유 덧붙이기 | "…, since … would otherwise …" |
| 사소함 | "nit: …" / "Non-blocking, but …" |
| 선택 | "Optional: …" / "Feel free to ignore." |
| 칭찬 | "Nice catch on …" / "This is much easier to follow now." |
| 후속 작업 | "Can we track this in a follow-up issue?" |
| 의견 철회 | "Good point, I missed that. Resolving." |

### 11.3 안티패턴

- **라벨 없는 코멘트** → 작성자가 전부 필수로 받아들임
- **근거 없는 취향 강요** → 스타일 가이드에 없으면 강요하지 않기
- **보지 않고 LGTM** → 승인은 "우리 기준을 충족한다"는 보증이어야 함
- **며칠 무응답 후 대규모 변경 요청** → 같은 요구라도 빠르게 응답하면 불만이 크게 줄어듦
- **코멘트를 하나씩 개별 제출** → 알림 폭탄. *Start a review*로 묶기
- **포매터·린터가 할 일을 사람이 지적** → 자동화로 넘기기
- **리뷰 창에서만 설명 마무리** → 코드나 주석에 남기도록
- **해결책 없는 문제 나열** → `issue`는 `suggestion`과 짝으로
- **나중에 정리하겠다는 약속만 믿고 승인** → 이슈 번호로 추적

## 12. 팀에 도입하기

- **라벨 체계 하나를 정해** `CONTRIBUTING.md`나 PR 템플릿에 명시합니다. (Conventional Comments가 범용, Pn 룰/L0~L5는 국내 팀에서 많이 차용)
- **GitHub Saved replies**(Settings → Saved replies)에 라벨 템플릿을 등록하면 단축키로 빠르게 삽입할 수 있습니다. ([14장](#14-부록-복붙용-saved-replies) 참고)
- Chrome/Firefox용 **Conventional Comments 확장 프로그램**을 쓰면 코멘트 박스에서 라벨을 자동완성할 수 있습니다.
- **스타일은 자동화**: 포매터(Prettier, Black, SwiftFormat 등)·린터·CI로 처리하고, 사람은 설계·로직에 집중합니다.
- **작은 PR 원칙**: 뱅크샐러드는 PR당 1,000줄 상한을 두었고, 실제로는 200~300줄 수준에서 1~2일 내 리뷰가 끝나도록 운영했습니다.
- **리뷰 기한 표기**(D-n 룰)로 리뷰어가 스스로 우선순위를 정하게 합니다.
- **PR 설명 템플릿**: 배경, 변경점, 테스트 방법, 스크린샷/GIF, 관련 문서 링크. 작성자가 미리 궁금할 만한 부분에 셀프 코멘트를 달아두면 리뷰 비용이 줄어듭니다.

## 13. 제출 전 셀프 체크리스트

- [ ] 각 코멘트에 의도·강도 **라벨**이 있는가?
- [ ] blocking 코멘트에 **재현 조건이나 근거**가 있는가?
- [ ] **코드**를 주어로 썼는가? (사람 X)
- [ ] **규칙**과 **취향**을 구분했는가?
- [ ] 구체적인 **칭찬**이 하나 이상 있는가?
- [ ] 한두 줄 수정은 **suggestion 블록**으로 줬는가?
- [ ] 범위 밖 제안은 **후속 이슈**로 분리했는가?
- [ ] **요약 코멘트**에 결론과 다음 행동이 있는가?
- [ ] 제출 **상태**(Approve / Comment / Request changes)가 코멘트 강도와 일치하는가?
- [ ] **1영업일** 안에 응답했는가?
